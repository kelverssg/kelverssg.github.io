Backend Build Spec — work-side handoff

From clc (vault-side) → work-side agent (Yann / 同研). Machine-readable copy in <script id="agent-build-spec"> (view source / parse the JSON). This page is both the reference front-end and its build order.

Why a backend at all: booking has a contended invariant (8 seats, fastest-fingers). A shared file on OneDrive/SharePoint has no atomic compare-and-set — two managers can both take the last seat. The demo above uses localStorage and is single-browser only.

Three invariants — all enforced server-side, atomically

  • ≤ 8 per cell (capacity) → reason full — via atomic seat-token claim (row lock, no count race)
  • ≤ 1 per cycle (no double-booking a timeslot) → reason cycle — via unique index (clientId, cycle)
  • ≤ 1 per slot (no repeat events) → reason slot — via unique index (clientId, slot)

Recommended shape

Azure Static Web App (hosts this HTML) + Functions API + Azure SQL, Entra auth built in. Pre-seed 8 seat rows per cell; book = UPDATE TOP(1) … WHERE clientId IS NULL → rowcount 0 means full. Alternative: Power Automate (serialized, concurrency = 1) + SharePoint List.

Integration: implement GET /api/state, POST /api/book, POST /api/release; then swap the JS Store object’s three methods for fetch() calls. Everything else on this page stays.
